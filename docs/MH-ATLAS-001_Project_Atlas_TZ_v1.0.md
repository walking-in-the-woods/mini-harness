## 2. Назначение и цели создания системы

### 2.1. Назначение

Atlas предназначен для формирования, хранения и предоставления LLM-агентам **компактного семантического представления кодовой базы** проекта с целью:

- снижения объёма контекста, необходимого агенту для навигации по проекту, не менее чем на 90%;
- обеспечения агентов детерминированной, верифицированной информацией о структуре, зависимостях и контрактах кода;
- исключения галлюцинаций при анализе структуры проекта;
- ускорения пакетной обработки однотипных сущностей (например, 25 функций с одинаковой сигнатурой).

### 2.2. Цели создания

1. Реализовать локальное хранилище графа проекта в формате SQLite.
2. Обеспечить инкрементальную переиндексацию по хешу файлов.
3. Предоставить LLM-агентам единый инструмент `atlas(op, arg, id)` с жёстким бюджетом ответа.
4. Реализовать модель «evidence with reasons» для предотвращения галлюцинаций.
5. Обеспечить работу на оборудовании класса Intel N100 с 8 ГБ RAM без GPU.

### 2.3. Область применения

Atlas применяется как встроенная подсистема mini-harness для локальной работы одного пользователя над Python-, JavaScript- и TypeScript-проектами. Многопользовательский режим, сетевое взаимодействие и облачные сервисы **не предусмотрены**.

## 4. Требования к системе

### 4.1. Требования к системе в целом

#### 4.1.1. Требования к структуре и функционированию

Система должна состоять из следующих подсистем:

1. **Indexer** — обход дерева проекта, парсинг исходных файлов, извлечение узлов и рёбер.
2. **Graph Store** — хранилище графа на базе SQLite с поддержкой FTS5.
3. **Evidence Engine** — формирование рёбер с категориями `confirmed` / `unresolved` и указанием причин.
4. **Capsule Formatter** — сериализация карточек в компактном формате с бюджетом токенов.
5. **Tool Facade** — единый инструмент `atlas(op, arg, id)` для LLM-агента.
6. **Lifecycle Manager** — управление индексацией: полной, инкрементальной, по триггерам.
7. **Sanitizer** — фильтрация потенциально опасного контента в карточках.

Все подсистемы должны быть реализованы на Python и работать в одном процессе с mini-harness без внешних сервисов.

#### 4.1.2. Требования к совместимости

- **ОС:** Linux (приоритет), macOS, Windows (WSL2).
- **Python:** 3.11+.
- **Зависимости:** SQLite 3.35+ (встроен в Python), tree-sitter (Python-биндинги), стандартная библиотека `ast`.
- **Запрещено:** Node.js, Docker, Kubernetes, внешние СУБД, облачные API.

#### 4.1.3. Требования к режимам функционирования

Система должна поддерживать:

- **Режим индексации** — построение/обновление графа.
- **Режим запросов** — обслуживание вызовов `atlas(...)`.
- **Режим простоя** — отсутствие фоновой активности (без watcher).
- **Режим отладки** — расширенное логирование и ручные команды `/atlas`.

### 4.2. Требования к функциональным характеристикам

#### 4.2.1. Indexer

**ФТ-1.** Система должна обходить дерево проекта, уважая `.gitignore` и исключая каталоги `__pycache__`, `.venv`, `node_modules`, `dist`, `build`.

**ФТ-2.** Система должна определять тип файла по расширению и выбирать парсер:

- `.py` → нативный `ast`;
- `.js`, `.jsx` → `tree-sitter-javascript`;
- `.ts`, `.tsx` → `tree-sitter-typescript`.

**ФТ-3.** Для Python-файлов система должна извлекать узлы типов: `Module`, `Class`, `Function`, `Method`, `Import`, `Decorator`, `Constant`.

**ФТ-4.** Для JS/TS-файлов система должна извлекать узлы типов: `Module`, `Function`, `ArrowFunction`, `Class`, `Component`, `Hook`, `Import`, `Export`.

**ФТ-5.** Для каждого узла должны извлекаться:

- полное имя (квалифицированное);
- путь к файлу;
- диапазон строк;
- сигнатура (для функций и методов);
- краткое summary (первая строка docstring/JSDoc);
- контракты (секции Args/Returns/Raises из docstring).

**ФТ-6.** Для каждого узла должны извлекаться рёбра типов:

- `contains` (модуль → класс/функция);
- `imports` (модуль → модуль);
- `calls` (функция → функция);
- `inherits` (класс → класс);
- `decorates` (декоратор → функция);
- `raises` (функция → исключение).

**ФТ-7.** Каждое ребро `calls`, `imports`, `inherits` должно иметь атрибут:

- `status`: `confirmed` | `unresolved`;
- `reason`: `import-binding` | `re-export-binding` | `binding-blocked` | `same-name` | `dynamic-dispatch` | `unknown`.

**ФТ-8.** Система должна поддерживать инкрементальную индексацию: переиндексация только файлов, чей хеш (SHA-256) изменился с момента последней индексации.

**ФТ-9.** Система должна поддерживать полную переиндексацию по команде `/reload`.

**ФТ-10.** Система должна корректно обрабатывать файлы с синтаксическими ошибками: пропускать их, фиксировать в логе, не прерывать индексацию.

#### 4.2.2. Graph Store

**ФТ-11.** Хранилище должно быть реализовано на SQLite и располагаться по пути `workspace/.atlas/graph.db`.

**ФТ-12.** Схема БД должна содержать таблицы:

- `nodes` (id, type, path, name, qualified_name, line_start, line_end, signature, summary, contracts, hash, generation);
- `edges` (id, source_id, target_id, type, status, reason, line, generation);
- `files` (path, hash, mtime, size, indexed_at, generation);
- `meta` (key, value);
- `nodes_fts` (виртуальная таблица FTS5 по name, qualified_name, summary).

**ФТ-13.** Все ID узлов должны быть детерминированными: `sha1(path::qualified_name)[:16]`.

**ФТ-14.** Хранилище должно поддерживать транзакционную запись: индексация одного файла — одна транзакция.

**ФТ-15.** Хранилище должно поддерживать запросы:

- поиск узла по ID;
- поиск узлов по подстроке имени (через FTS5);
- получение входящих и исходящих рёбер узла;
- получение полного пути (transitive closure) до заданной глубины (≤ 3).

#### 4.2.3. Evidence Engine

**ФТ-16.** Для каждого ребра `calls` движок должен пытаться разрешить привязку:

- через прямой импорт → `confirmed`, `import-binding`;
- через реэкспорт → `confirmed`, `re-export-binding`;
- при наличии одноимённого символа без привязки → `unresolved`, `same-name`;
- при динамическом вызове (`getattr`, `**kwargs`, `eval`, DI-контейнер) → `unresolved`, `dynamic-dispatch`.

**ФТ-17.** Ответы движка должны содержать явные счётчики:

- количество `confirmed` рёбер;
- количество `unresolved` рёбер;
- распределение `unresolved` по причинам.

**ФТ-18.** Движок не должен возвращать предположения как факты. Любое ребро без подтверждённой привязки помечается как `unresolved`.

#### 4.2.4. Capsule Formatter

**ФТ-19.** Форматтер должен формировать карточки узлов в следующих режимах:

| Операция | Содержимое | Бюджет токенов |
| --- | --- | --- |
| `overview` | Проект, стек, пакеты, entrypoints | ≤ 200 |
| `search` | До 10 совпадений `path::symbol` | ≤ 80 |
| `card` | Карточка узла (см. 4.2.5) | ≤ 150 |
| `callers` | До 10 входящих `calls` с evidence | ≤ 100 |
| `callees` | До 10 исходящих `calls` с evidence | ≤ 100 |
| `impact` | До 10 узлов, зависящих от заданного | ≤ 120 |

**ФТ-20.** При превышении бюджета форматтер должен обрезать результат с пометкой `[truncated]` в конце.

**ФТ-21.** Форматтер должен использовать компактный синтаксис (без JSON-обёрток, без избыточных пробелов), ориентированный на токенизацию LLM.

**ФТ-22.** Каждая карточка должна содержать `generation_hash` — хеш поколения индекса, к которому она относится.

#### 4.2.5. Формат карточки узла

Карточка функции должна содержать:

- квалифицированное имя;
- сигнатуру;
- summary (одна строка, ≤ 100 символов);
- список вызываемых функций (до 5, только имена);
- контракты (исключения, side effects) — если есть;
- ссылку на тесты — если есть;
- `generation_hash`.

Карточка модуля должна содержать:

- путь;
- summary (1–2 предложения, ≤ 200 символов);
- публичный API (до 10 имён);
- зависимости (до 10 модулей);
- зависимые (до 10 модулей);
- `generation_hash`.

Карточка класса должна содержать:

- квалифицированное имя;
- базовые классы;
- публичные методы (до 10 имён);
- summary (≤ 150 символов);
- `generation_hash`.

#### 4.2.6. Tool Facade

**ФТ-23.** Система должна предоставлять LLM-агенту **ровно один** инструмент с именем `atlas`.

**ФТ-24.** Схема инструмента должна занимать не более 80 токенов и иметь вид:

```text
atlas(op: enum[overview, search, card, callers, callees, impact],
      arg: str,
      id: str = "")
```

**ФТ-25.** Инструмент должен быть **строго read-only**. Ни одна операция `atlas` не должна изменять файлы проекта, граф или конфигурацию.

**ФТ-26.** Инструмент должен возвращать результат в формате, совместимом с текущим Tool Registry mini-harness.

**ФТ-27.** Вызовы `atlas` не должны накапливаться в истории диалога. Результат каждого вызова используется один раз и не сохраняется в контексте.

#### 4.2.7. Lifecycle Manager

**ФТ-28.** Система должна поддерживать команды mini-harness:

- `/atlas overview` — ручной вызов Root View для отладки;
- `/atlas rebuild` — полная переиндексация;
- `/atlas refresh` — инкрементальная переиндексация;
- `/atlas stats` — статистика по графу (число узлов, рёбер, размер БД).

**ФТ-29.** При старте сессии mini-harness система должна:

- проверить наличие `graph.db`;
- если БД отсутствует — выполнить полную индексацию;
- если БД есть — проверить `generation_hash` и выполнить инкрементальное обновление.

**ФТ-30.** Система **не должна** запускать фоновый watcher файловой системы. Обновление выполняется только по явному триггеру (`/reload`, `/atlas refresh`, старт сессии).

#### 4.2.8. Sanitizer

**ФТ-31.** При формировании карточек система должна фильтровать потенциально опасный контент:

- обрезать строки до 200 символов;
- удалять символы `#`, обратные кавычки, переводы строк из полей name/summary;
- выявлять и удалять паттерны, похожие на prompt injection (`ignore previous`, `system:`, `<|im_start|>` и т. п.);
- заменять удалённый контент на маркер `[filtered]`.

**ФТ-32.** Все ID в карточках должны быть внутренними (сгенерированными системой), не содержать пользовательских путей в открытом виде.

### 4.3. Требования к надёжности

**ФТ-33.** Индексация должна быть идемпотентной: повторный запуск на неизменённых файлах не должен изменять БД.

**ФТ-34.** При сбое индексации (например, OOM) система должна сохранять консистентное состояние БД: незавершённые транзакции откатываются.

**ФТ-35.** При повреждении `graph.db` система должна обнаруживать это (например, через `PRAGMA integrity_check`) и предлагать полную переиндексацию.

**ФТ-36.** Все ошибки индексации должны логироваться в `logs/atlas.log` без прерывания работы mini-harness.

### 4.4. Требования к безопасности

**ФТ-37.** Atlas должен работать **только локально**, без сетевых соединений.

**ФТ-38.** Atlas не должен содержать телеметрии, аналитики и внешних вызовов.

**ФТ-39.** Atlas не должен читать файлы за пределами корня проекта (защита от path traversal).

**ФТ-40.** Atlas не должен выполнять код из анализируемых файлов (только статический анализ).

**ФТ-41.** Atlas не должен использовать `eval`, `exec`, `pickle` и иные небезопасные механизмы десериализации.

**ФТ-42.** Секреты (API-ключи, токены, пароли), обнаруженные в исходниках, не должны попадать в карточки. Система должна выявлять паттерны (`password=`, `api_key=`, `token=`, `sk-...`, `ghp_...`) и заменять их на `[redacted]`.

### 4.5. Требования к лицензированию

**ФТ-43.** Все заимствованные фрагменты кода должны сопровождаться уведомлениями об авторских правах:

- для **Osnova** (Apache 2.0): сохранить файл `LICENSE`, добавить `NOTICE` при наличии, пометить изменённые файлы;
- для **ctxgraph-code** (MIT): сохранить текст лицензии и копирайт.

**ФТ-44.** В корне репозитория mini-harness должен быть создан файл `THIRD_PARTY_LICENSES.md` с перечислением всех заимствованных компонентов.

**ФТ-45.** Итоговое решение может распространяться под любой лицензией по выбору Заказчика, при условии соблюдения ФТ-43 и ФТ-44.

## 5. Требования к нефункциональным характеристикам

### 5.1. Требования к производительности

**НФТ-1.** Полная индексация проекта из 3000 файлов Python на N100 должна занимать не более **60 секунд**.

**НФТ-2.** Инкрементальная переиндексация при изменении 10 файлов должна занимать не более **2 секунд**.

**НФТ-3.** Время ответа на запрос `atlas(op, arg, id)` не должно превышать **50 мс** (без учёта сетевых задержек, которых нет по определению).

**НФТ-4.** Размер `graph.db` для проекта из 3000 файлов не должен превышать **200 МБ**.

**НФТ-5.** Потребление RAM подсистемой Atlas не должно превышать **100 МБ** в режиме запросов и **300 МБ** в режиме полной индексации.

### 5.2. Требования к качеству контекста

**НФТ-6.** Ответ `atlas(op="overview")` должен укладываться в **200 токенов**.

**НФТ-7.** Ответ `atlas(op="card")` должен укладываться в **150 токенов**.

**НФТ-8.** Совокупный объём контекста, занимаемый инструментом `atlas` (схема + один ответ + инструкция в промпте), не должен превышать **400 токенов** при num_ctx=2048 (≈ 20% бюджета).

**НФТ-9.** Сокращение контекста при использовании Atlas вместо чтения файлов должно быть не менее **90%** для типовых запросов навигации.

### 5.3. Требования к надёжности и отказоустойчивости

**НФТ-10.** Система должна корректно работать при 8 ГБ RAM без swap-файла.

**НФТ-11.** Система не должна блокировать работу mini-harness при индексации: индексация должна быть асинхронной.

**НФТ-12.** При превышении лимита RAM система должна прерывать индексацию с сохранением промежуточного состояния.

### 5.4. Требования к удобству эксплуатации

**НФТ-13.** Установка Atlas должна сводиться к:

- добавлению зависимостей в `requirements.txt`;
- запуску `pip install -r requirements.txt`.

**НФТ-14.** Первичная инициализация Atlas должна выполняться автоматически при первом `/reload`.

**НФТ-15.** Пользователь должен получать понятные сообщения об ошибках индексации на русском языке.

### 5.5. Требования к совместимости с существующим кодом

**НФТ-16.** Atlas не должен требовать изменения существующих команд mini-harness (`/tree`, `/files`, `/dump`, `/reload`, `/batch`, `/sources`).

**НФТ-17.** Существующие prompt-файлы (`tree-summary.md`, `tree-summary-detailed.md`) должны быть расширены, а не заменены.

**НФТ-18.** Интеграция Atlas не должна нарушать текущее поведение `/batch`.

## 7. Требования к информационному обеспечению

### 7.1. Входные данные

- исходные файлы проекта (`.py`, `.js`, `.jsx`, `.ts`, `.tsx`);
- `workspace/sources.yaml` — список источников;
- `config.yaml` — конфигурация Atlas.

### 7.2. Выходные данные

- `workspace/.atlas/graph.db` — граф проекта;
- `logs/atlas.log` — лог индексации и ошибок;
- ответы инструмента `atlas(...)` в формате capsule.

### 7.3. Форматы обмена

- ответы `atlas` — плоский текст (не JSON), ориентированный на LLM-токенизацию;
- внутренние структуры — Python dataclasses;
- персистентность — SQLite.

## 10. Этапы разработки

### Этап 1. MVP: Python-only Atlas (2–3 недели)

- Indexer для Python (AST).
- Graph Store (SQLite, схема).
- Базовая версия Evidence Engine (`import-binding`).
- Formatter с жёсткими бюджетами.
- Tool Facade с одной схемой.
- Lifecycle: `/atlas rebuild`, `/atlas stats`.
- Sanitizer (базовая версия).
- Документация.

**Критерий приёмки этапа:** `atlas(op="card", arg="module::func")` работает на реальном Python-проекте, ответ укладывается в 150 токенов.

### Этап 2. JS/TS и инкрементальная индексация (2 недели)

- Парсеры tree-sitter для JS/TS.
- Расширенный Evidence Engine (`re-export-binding`, `same-name`, `dynamic-dispatch`).
- Инкрементальная индексация по хешу.
- Команды `/atlas refresh`.
- Расширенный Sanitizer (redaction секретов).

**Критерий приёмки этапа:** инкрементальная переиндексация 10 файлов ≤ 2 секунд.

### Этап 3. Оптимизация и интеграция с /batch (2 недели)

- Кэширование карточек (LRU).
- Оптимизация запросов SQLite (индексы, EXPLAIN QUERY PLAN).
- Расширение `/batch`: группировка похожих символов через Atlas.
- Финальная документация и тесты.

**Критерий приёмки этапа:** batch из 25 однотипных функций обрабатывается за ≤ 5 минут вместо 40.

### Этап 4. Стабилизация (1 неделя)

- Нагрузочное тестирование на N100.
- Проверка на утечки памяти.
- Проверка безопасности (path traversal, injection, secrets).
- Финальное ревью.

## 11. Критерии приёмки системы

### 11.1. Функциональные критерии

- **ПК-1.** Все функциональные требования ФТ-1 — ФТ-45 выполнены и подтверждены тестами.
- **ПК-2.** Atlas работает на реальном проекте из ≥ 1000 файлов без ошибок индексации.
- **ПК-3.** Инструмент `atlas` корректно вызывается LLM-агентом (4B-модель) без дополнительного обучения.

### 11.2. Нефункциональные критерии

- **ПК-4.** Все нефункциональные требования НФТ-1 — НФТ-18 выполнены.
- **ПК-5.** Установка и запуск воспроизводятся на чистой системе N100 с 8 ГБ RAM за ≤ 10 минут.
- **ПК-6.** Потребление RAM в режиме запросов ≤ 100 МБ.

### 11.3. Критерии качества контекста

- **ПК-7.** Ответ `atlas(op="overview")` ≤ 200 токенов на реальном проекте.
- **ПК-8.** Ответ `atlas(op="card")` ≤ 150 токенов.
- **ПК-9.** Сокращение контекста при навигации ≥ 90% относительно чтения файлов.

### 11.4. Критерии безопасности

- **ПК-10.** Atlas read-only: ни один вызов не изменяет файлы проекта.
- **ПК-11.** Нет сетевых соединений при работе Atlas.
- **ПК-12.** Sanitizer блокирует тестовые injection-паттерны.
- **ПК-13.** Redactor заменяет тестовые секреты на `[redacted]`.

## 12. Требования к тестированию

### 12.1. Модульные тесты

- Парсеры Python и JS/TS на эталонных файлах.
- Evidence Engine на синтетических случаях (`import-binding`, `same-name`, `dynamic-dispatch`).
- Capsule Formatter: контроль бюджета токенов.
- Sanitizer: набор тестовых injection-паттернов и секретов.
- Graph Store: CRUD, транзакции, FTS5-запросы.

### 12.2. Интеграционные тесты

- Полный цикл: индексация → запрос → ответ.
- Инкрементальная индексация при изменении файла.
- Работа с реальным проектом (mini-harness сам по себе).

### 12.3. Нагрузочные тесты

- Индексация 3000 файлов на N100.
- 1000 последовательных запросов `atlas(op="card")`.
- Проверка утечек памяти (tracemalloc).

### 12.4. Тесты безопасности

- Path traversal (попытка чтения `/etc/passwd`).
- Prompt injection через docstring.
- Redaction секретов (`api_key`, `token`, `password`).

### 12.5. Тесты совместимости

- Работа с Python 3.11, 3.12, 3.13.
- Работа с SQLite 3.35+.
- Отсутствие Node.js в системе.
