# Внешние источники

## Зачем

`workspace/` — единственная директория, которую модель видит через
`read_file`. Иногда нужно **показать модели проект или базу знаний**,
лежащие вне workspace. Для этого — внешние источники.

Source — read-only корень за пределами workspace, который
пользователь явно разрешил. Harness читает источник и складывает
результат в `workspace/input/`, откуда модель читает обычным
`read_file`. **Модель не имеет прямого доступа к внешнему пути** —
только к сгенерированному снимку.

## Конфигурация

Файл: `workspace/sources.yaml`. Шаблон: `workspace/sources.yaml.example`.

```yaml
defaults:
  max_depth: 0             # 0 = без ограничений
  max_tree_entries: 0      # 0 = без ограничений
  max_entries: 500         # для /files
  max_files: 200           # для /dump
  max_file_bytes: 50000
  max_total_bytes: 200000
  ignore:
    dirs: ["**/.git/**", "**/node_modules/**"]
    files: ["**/*.lock"]

sources:
  - name: myproject
    root: ~/projects/myproject
    description: "Рабочая копия, ветка main"

  - name: knowledge
    root: /mnt/data/wiki
    max_depth: 8
```

## Команды REPL

Все команды — **пользователя**, не модели. Результат в `workspace/input/`.

| Команда | Что создаёт |
| --- | --- |
| `/sources` | список источников и их статус |
| `/reload` | перечитать `sources.yaml` |
| `/tree <name> [subpath]` | `input/_tree_<name>.md` — дерево |
| `/files <name> [subpath]` | `input/_files_<name>.md` — плоский список с размерами |
| `/dump <name> [subpath]` | `input/_dump_<name>.md` — содержимое файлов |

## Типовой сценарий

Показать модели структуру проекта:

```sh
>>> /tree myproject
[+] _tree_myproject.md  (1247 entries, 38210 bytes)

>>> прочитай input/_tree_myproject.md и опиши структуру проекта
```

Суммаризировать модуль:

```sh
>>> /dump myproject src/auth/
[+] _dump_myproject.md  (12 files, 43210 bytes)

>>> прочитай input/_dump_myproject.md и напиши резюме архитектуры в output/auth_summary.md
```

Здесь `dump` сработал **второй раз** на подкаталоге — перезаписал
предыдущий `_dump_myproject.md`. Файл один на источник, не плодит
мусор. Если нужны разные срезы — используйте `/dump` с разными
source-именами.

## Почему tree и dump раздельно

- **Tree** — компактное представление (десятки строк) даже для
  большого проекта. Показывает общую структуру. Не тратит контекст
  модели на содержимое.
- **Dump** — содержимое конкретных файлов. Нужен, когда важно
  прочитать код целиком.
- **Files** — промежуточный формат: список путей с размерами, без
  структуры и без содержимого. Полезен для поиска («где лежит файл
  X?») или для оценки объёма до `/dump`.

Один `/dump` сразу по корню проекта часто даёт файл на сотни
килобайт, который модель физически не сможет прочитать. Поэтому
практика такая: **сначала `/tree`, выбрать подкаталог, потом `/dump`
на подкаталоге**.

## Лимиты по командам

Разные команды — разные лимиты, потому что данные разного рода:

| Команда | Глубина | Количество | Размер |
| --- | --- | --- | --- |
| `/tree` | без ограничений | без ограничений | — |
| `/files` | без ограничений | `max_entries: 500` | — |
| `/dump` | без ограничений | `max_files: 200` | `max_file_bytes`, `max_total_bytes` |

**Глубина не ограничена нигде.** В реальных проектах вложенность
непредсказуема: 3 уровня в одном, 12 в другом. Обрезка по глубине
портит структуру без причины. От symlink-циклов защищает детектор
`visited` — если `realpath` элемента уже пройден в текущем обходе,
элемент пропускается. Это точнее и не режет нормальные случаи.

**`/tree` не обрезается по количеству записей.** Дерево — только
пути, ~30 байт на строку. 100k файлов ≈ 3 МБ, что открывается в
редакторе. Смысл команды теряется, если показать половину структуры.

**`/dump` по-прежнему ограничен жёстко.** Содержимое файлов —
единственное, где неограниченный объём даст гигабайты.

### Патологический случай `root: /`

Без `max_depth` обход `/` зайдёт в `/proc`, `/sys`, `/dev` и будет
читать псевдофайлы, пока не упрётся в permission-ошибки. Это не
бесконечность (цикл-детектор работает), но много мусора.

Решение — явный `max_depth` или `ignore`-паттерны:

```yaml
sources:
  - name: rootfs
    root: /
    max_depth: 4
    ignore:
      dirs:
        - "**/proc/**"
        - "**/sys/**"
        - "**/dev/**"
        - "**/run/**"
```

`max_depth > 0` включает ограничение; `0` (дефолт) — выключено.

### Symlink-циклы

Если в источнике есть symlink, ведущий на предка (`a/b -> a`),
обход не уйдёт в бесконечную рекурсию. Детектор `visited` хранит
`realpath` каждой посещённой директории в текущем обходе; при
повторной попытке войти в уже пройденный каталог обход обрывается
на этой ветке. Ни ошибки, ни зависания — просто пропуск.

### Когда дерево слишком большое для модели

При `NUM_CTX=1024` модель читает ~3000 символов. Это ~100 строк
дерева. Если tree содержит 5000 файлов — guided mode обрежет
источник до первых 3000 символов, и модель увидит только верхний
уровень.

Практический приём: **`/tree` на подкаталоге**. Вместо `/tree myproj`
— `/tree myproj src/auth`, где файлов меньше. Дерево остаётся
неограниченным, но выбирается осмысленный срез.

## Безопасность

- **Realpath внутри source.** Symlink, ведущий за пределы
  `source.root`, пропускается целиком. Проверка идёт на каждом
  элементе обхода.
- **Детектор циклов.** `visited: set[Path]` из `realpath`. Защита
  от symlink loop и любых алиасов внутри source.
- **Чёрный список `config.yaml`** (`**/.env`, `**/*.key`,
  `**/.ssh/**`, ...) применяется и к внешним источникам.
- **Собственный `ignore` источника** добавляется поверх.
- **Subpath не может выйти за source.** `../etc` → `SourceError`.
- **Внешние файлы не модифицируются.** Никакого write-API у
  `SourceRegistry` нет. Только чтение.
- **Команды — привилегия пользователя.** Они не парсятся моделью,
  не приходят из `agent.run()`. Harness сам пишет результат в
  `workspace/input/`, минуя `FileSystemGuard` — но это write **в
  workspace**, не в источник.

## Лимиты контекста

Реальный размер контекста модели на N100 при `NUM_CTX=1024` —
примерно 2000 символов кириллицы или 4000 символов латиницы. Это
**очень мало**. Практические выводы:

1. **`/tree` — безопасен.** 40-100 строк дерева влезают в контекст
   целиком. Если дерево большое — читайте его в редакторе, а
   модели давайте подкаталог.
2. **`/dump` — только на маленький подкаталог.** Если dump больше
   `NUM_CTX * 3` символов, guided mode его обрежет с пометкой.
3. **`max_total_bytes`** разумно держать в диапазоне 2000-10000
   для машин с маленьким контекстом. Дефолтные 200 000 — это
   «прочитать целиком файл» (через обычный `read_file`), но для
   суммирования через guided mode столько не нужно.

Настройка в `sources.yaml`:

```yaml
defaults:
  max_total_bytes: 8000        # ~2-4K токенов
  max_file_bytes: 3000         # отдельный файл ~1.5K токенов
```

## Формат вывода dump

Для `.md`-файлов внутри dump используется **четыре** бэктика в
качестве fence. Открывающий и закрывающий — по четыре:

````markdown
# Заголовок
Текст с вложенным ```code``` — не ломает внешний блок.
````

Это делается потому, что в `.md`-файлах источника часто есть свои
блоки кода с тремя бэктиками. Если обернуть такой файл тремя
бэктиками, разметка dump'а поедет. Четыре бэктика — устойчивее.

Обратите внимание: в примере выше показан **текстовый вид** того,
что генерирует инструмент. Здесь он обёрнут в `text`-блок с
**тремя** бэктиками, а внутри — четыре. Если вы копируете пример
в свой файл, берите только содержимое, без внешнего `text`-блока.

Для остальных расширений — обычные три бэктика с language-тегом
(`python`, `json`, `yaml`, ...).

## Что в `.gitignore`

`workspace/sources.yaml` **исключён** через `workspace/*`, потому
что содержит пользовательские пути (могут быть чувствительные:
`~/secrets`, `/mnt/private`). Если хотите коммитить — добавьте в
`.gitignore` исключение:

```text
!workspace/sources.yaml
!workspace/sources.yaml.example
```

Шаблон `sources.yaml.example` коммитится всегда.
