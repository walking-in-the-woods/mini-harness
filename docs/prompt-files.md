# Prompt-файлы

## Что это

Файл с текстовой инструкцией, который подставляется модели вместо
встроенного system-промпта в guided mode. Позволяет задавать
специфические правила для конкретного типа задачи (описать проект,
перевести строго по глоссарию, извлечь структуру) — без правки
Python-кода.

Prompt-файл — это **данные**, не код. Его можно менять, коммитить,
тестировать как обычный текст. Harness не перезапускается.

## Синтаксис

Два способа указать prompt-файл в запросе.

### 1. Явный маркер

```sh
>>> прочитай input/_tree_harness.md согласно инструкции из input/prompts/tree-summary.md, результат в output/overview.md
```

Поддерживаемые маркеры (регистронезависимо, русские и английские):

| Маркер | Пример |
| --- | --- |
| `по инструкции из` | `…согласно инструкции из input/prompts/x.md` |
| `согласно инструкции` | `…по инструкции input/prompts/x.md` |
| `с промптом` / `по промпту` | `…прочитай input/a.md с промптом input/prompts/x.md` |
| `using prompt` / `with prompt` | `…read input/a.md using prompt input/prompts/x.md` |
| `following prompt` / `per prompt` | `…summarize input/a.md following prompt input/prompts/x.md` |

Путь после маркера — до следующего пробела, с расширением `.md`,
`.txt` или `.markdown`.

### 2. Соглашение `input/prompts/`

Любой путь под `input/prompts/` автоматически считается prompt-файлом,
даже без маркера:

```sh
>>> прочитай input/_tree_harness.md и примени input/prompts/tree-summary.md, результат в output/overview.md
```

Это работает и когда в запросе нет ключевого слова операции
(«резюме», «переведи»): операция становится `custom`, guided mode
запускается с prompt-файлом.

### Приоритет

Маркер имеет приоритет над соглашением. Если маркер указывает на
несуществующий файл — prompt-файл считается отсутствующим, guided
mode работает со встроенным `_TRANSFORM_SYSTEM`.

## Как это работает

1. Парсер извлекает из запроса три роли: **source** (что читать),
   **target** (куда писать), **prompt** (чем руководствоваться).
2. Harness читает prompt-файл и **полностью заменяет** им слот
   `system` в запросе к модели.
3. User message содержит только источник и нейтральную фразу
   «примени инструкцию из системного сообщения».
4. Модель получает **один** вызов без tools.
5. Результат пишется в target через обычный nonce.

Проверить, что prompt-файл подхватился, можно по строке в stderr:

```sh
[*] guided mode: custom input/_tree_harness.md -> output/overview.md [prompt: input/prompts/tree-summary.md]
[*] custom model output: '...' (N chars)
```

Тег `custom model output` — вместо `first model output`. Если видите
`[prompt: built-in]` — файл не найден или маркер не распознан.

## Retry не работает с prompt-файлами

Для встроенного промпта harness делает вторую попытку, если результат
короче 30 символов или является подстрокой исходника. Для custom
prompt retry не срабатывает: harness не знает, какой формат вы
ожидаете, и не может судить о качестве по размеру.

Если результат с custom prompt плохой — правьте prompt-файл, не
ждите автоматического исправления.

## Потолок модели: 1.7B — не работает, 3B — на грани, 4B+ — работает

Это самый важный раздел. Он документирует результат нескольких
итераций и объясняет, почему качество ответа зависит от модели,
а не от harness.

### Наблюдение: имена файлов превращаются в директории

С фразой «назови директории (не отдельные файлы)» 1.7B перестаёт
перечислять `audit.py`, `proxy.py`, `main.py` как «директории».
Но появляется новая ошибка: `sources.py` превращается в `sources/`.
Модель знает, что в дереве есть что-то с основой `sources`, и
достраивает логичную директорию — по аналогии с `harness/`,
`docs/`, `tests/`, которые действительно директории.

Три из четырёх названных директорий оказываются правильными.
Четвёртая — синтетическая. Это предел интерпретации иерархии
для моделей этого класса, не bug harness.

### Что было проверено

Три модели, один и тот же источник (дерево `mini-harness`, 67
записей), один prompt-файл. Менялся только текст prompt-файла
и модель.

| Модель | Версия prompt-файла | Результат |
| --- | --- | --- |
| qwen3:1.7b | 4 абзаца, оба примера | 1221 символов, реальные директории, повторы |
| qwen3:1.7b | 3 абзаца, оба примера | 445 символов, **копия «хорошего» примера** |
| qwen3:1.7b | 3 абзаца, только «плохой» | 286 символов, перечень файлов, игнорирует правила |
| llama3.2:3b | 3 абзаца, только «плохой» | 282 символа, **копия «плохого» примера** |

**Вывод:** модели до 4B **копируют любой пример из промпта
дословно**, независимо от того, помечен он как «хороший» или
«плохой». Few-shot — техника для 4B+, для меньших моделей она
работает как шаблон, который надо воспроизвести.

### Правила для prompt-файлов при работе с моделями < 4B

1. **Никаких примеров.** Ни «хороших», ни «плохих». Любой фрагмент
   текста в system-промпте, похожий на ответ, будет скопирован.

2. **Никаких списков и нумерации внутри инструкции.** Строки вида
   «1. Сделай X. 2. Сделай Y.» воспроизводятся как заголовки.

3. **Никаких меток абзацев.** «**Первый абзац**» в инструкции
   становится «**Первый абзац**» в ответе.

4. **Прозой, не bullet-поинтами.** «Скажи, что это за проект. Назови
   3-4 ключевые директории.» работает лучше, чем:
   - что это за проект
   - какие директории
   - какие технологии

5. **Минимум правил.** Одно правило из пяти работает, пять из пяти —
   не работают. Модель не удерживает больше двух-трёх инструкций
   одновременно.

6. **Запреты работают лучше разрешений.** «Не выдумывай директории,
   которых нет в дереве» — работает. «Используй только реальные
   директории» — нет.

### Что реально может 1.7B / 3B

**Может:**

- Суммаризация связного текста (2-4 предложения).
- Простые преобразования: перевод, переписывание.
- Извлечение структуры из абзаца (в каком виде, какие поля).
- Перечисление имён файлов из дерева.

**Не может:**

- Описать проект по дереву с правильной типизацией («агент», а не
  «фреймворк для данных»).
- Следовать многострочной инструкции с абстрактными правилами.
- Не повторять одну мысль в разных абзацах.
- Отличить пример «как надо» от примера «как не надо».

### Что делать для качественного описания проекта

Нужна модель от 4B. На машине с 16 ГБ RAM — `qwen3:8b` или больше.
Промпт-файл для них может быть полнее: с примерами, списками,
несколькими абзацами правил.

## Пример: `tree-summary.md`

Канонический пример — описание структуры проекта по дереву файлов.
Лежит в `workspace/input/prompts/tree-summary.md`.

### Содержимое

Полный текст — короткий, потому что рассчитан на 1.7B. Ключевые
элементы:

**Три темы в одном абзаце.** «Скажи, что это за проект. Назови
3-4 значимые директории. Упомяни инструменты.» — одна инструкция,
которая порождает три предложения ответа. Не три отдельных пункта,
которые модель может перепутать.

**Один запрет в конце.** «Не выдумывай директории и файлы, которых
нет в дереве» — против галлюцинации `src/`, характерной для моделей,
обученных на типичных Python-проектах.

**Явный язык.** «На русском языке» — потому что источник содержит
латинские имена файлов, и без указания модель может ответить
по-английски.

### Ожидаемый результат

Для дерева из ~60 записей на 1.7B или 3B:

- Длина: 200-400 символов.
- 2-3 предложения связного текста.
- Реальные директории (`harness/`, `docs/`, `tests/`), без `src/`.
- Возможны неточности в типизации проекта.

Это **потолок** для моделей этого класса. Не идеальное описание,
но честное — модель перечисляет реальные директории и не выдумывает.

### История улучшений

Первые версии prompt-файла содержали примеры «хорошего ответа» —
модель копировала их вместо анализа источника, добавляя в результат
несуществующие `src/`, Sphinx, httpx. Убрали оба примера. Оставили
только «плохой» как иллюстрацию повторов — модель 3B скопировала
и его.

Финальная версия — без каких-либо примеров, только прозаическая
инструкция. Меньше текста, меньше шума, меньше возможностей
для копирования.

## Как писать свой prompt-файл

1. **Одна тема — одно предложение инструкции.** Если задача сложная,
   разбейте её на несколько запусков guided mode, а не в один
   prompt-файл.

2. **Императив, прозой.** «Опиши проект. Назови директории. Упомяни
   технологии.» Не «нужно, чтобы ты описал…» и не bullet-список.

3. **Запреты в конце.** Последнее правило модель читает внимательнее
   всего. «Не выдумывай», «не пересказывай», «не копируй» — ставьте
   в конец.

4. **Не давайте примеров для 1.7B / 3B.** Примеры копируются. Если
   очень хочется показать формат — опишите его словами: «связный
   текст, без заголовков».

5. **Явный язык.** «На русском языке» — единственный способ
   заставить слабую модель не переключаться на английский при
   латинских именах в источнике.

6. **Тестируйте на своём источнике.** Разные деревья, разные
   вопросы. Один prompt-файл может хорошо работать для одного
   проекта и плохо для другого.

## Что не поддерживается

- **Несколько prompt-файлов.** Только один, найденный по маркеру
  или соглашению.
- **Промпт-файлы для `/tree`, `/files`, `/dump`.** Это команды
  пользователя для просмотра, они не вызывают модель.
- **Многошаговые prompt-файлы** («сначала сделай X, потом Y»).
  Модель в guided mode не имеет tools и не может вызвать read_file.
- **Автоматический retry.** См. выше — только для встроенного промпта.
- **Few-shot примеры для моделей < 4B.** См. раздел «Потолок модели».
